## 2. Blueprint 02 — Nginx edge security

Các điểm đã hoàn thành:

- Chuẩn hóa CSP và các security header dùng chung giữa response HTML, static asset, SPA fallback và lỗi do Nginx sinh ra.
- Đồng bộ upload limit tại edge; payload quá giới hạn trả JSON HTTP 413 với mã ứng dụng `1019`.
- Chỉ ghi đè forwarded header từ reverse proxy tin cậy, không nối tiếp header tùy ý do client gửi lên.
- SSE được tắt proxy buffering để notification không bị giữ trong buffer.
- Frontend container chạy bằng Nginx unprivileged và có healthcheck dùng IPv4 loopback ổn định.
- Ba Nginx contract test đạt; cấu hình Compose được Docker parse thành công.
- Local runtime đã xác nhận proxy `/api`, CSP, upload limit và SPA fallback/deep-link hoạt động trong container.

Lý do cải thiện:

- Security header phải xuất hiện nhất quán trên cả response thành công lẫn lỗi; nếu chỉ khai báo ở một location, browser có thể nhận chính sách khác nhau tùy URL.
- Upload limit tại Nginx giảm tải trước khi request lớn đi vào JVM, đồng thời giữ response contract mà frontend hiểu được.
- Forwarded header chính xác là điều kiện để rate limit theo IP không bị giả mạo hoặc gom mọi người dùng vào IP của proxy.

Phần còn chờ:

- Xác nhận HTTPS, HSTS và chuỗi trusted proxy trên hạ tầng staging thật.

## 3. Blueprint 03 — Backend production configuration

Các điểm đã hoàn thành:

- Cấu hình production dùng typed properties và fail-fast khi thiếu database, SMTP, OAuth, Cloudinary, JWT, pepper, application URL hoặc CORS origin.
- MySQL production bắt buộc chính sách TLS phù hợp, gồm `sslMode=VERIFY_IDENTITY`.
- URL ứng dụng và CORS production bắt buộc HTTPS, không âm thầm fallback về localhost.
- Admin bootstrap chỉ chạy cho database chưa có admin, yêu cầu password được cấp rõ ràng và không giữ password mặc định.
- Đồng bộ multipart limit với giới hạn ảnh của service: file tối đa 2 MB, request tối đa 3 MB.
- Bổ sung kiểm tra kích thước ảnh sau giải mã để ngăn ảnh có số pixel quá lớn dù dung lượng nén nhỏ.
- Toàn bộ **83 backend test** đạt, bao gồm validator production, admin bootstrap, multipart exception và image-dimension validation.

Lý do cải thiện:

- Production phải dừng ngay khi cấu hình sai thay vì khởi động với localhost, HTTP hoặc credential rỗng rồi thất bại muộn.
- Kiểm tra TLS và HTTPS bảo vệ credential/token trên đường truyền khi triển khai ra Internet.
- Giới hạn cả byte lẫn pixel giảm rủi ro làm cạn bộ nhớ khi backend giải mã ảnh nén độc hại.

Phần còn chờ:

- Khởi động profile production với database, hostname, certificate và secret thật trên staging.

## 4. Blueprint 04 — Docker rehearsal

### 4.1. Stack rehearsal

- Hoàn tất stack `cgfoodtour-rehearsal` gồm MySQL 8.0, backend, frontend/Nginx và Mailpit.
- Chọn MySQL 8.0 vì phù hợp dải phiên bản đã được Flyway 11.7.2 hỗ trợ/kiểm chứng; tránh dùng MySQL 8.4 khi compatibility chưa chắc chắn.
- Cả bốn container đạt trạng thái healthy.
- Greenfield database chạy Flyway rồi Hibernate `ddl-auto=validate` thành công.
- Backend image chạy UID `10001`; frontend image chạy UID `101`, không chạy application process bằng root.
- Backend image có kích thước `158,231,667` bytes; frontend image `22,541,673` bytes.

### 4.2. Image storage dành riêng cho rehearsal

- Tạo `ImageStorageService` làm contract dùng chung cho upload/delete ảnh.
- `CloudinaryService` là implementation ngoài profile rehearsal.
- `RehearsalImageStorageService` chỉ hoạt động với profile `rehearsal`, tạo URL/public ID giả lập mà không cần Cloudinary credential hoặc quota thật.
- `ManagedImageService` và `MediaCleanupQueueService` phụ thuộc interface thay vì implementation Cloudinary cụ thể.
- Thêm cờ rehearsal mô phỏng lỗi xóa ảnh để kiểm tra cleanup queue.

Lý do cải thiện:

- Local rehearsal cần kiểm tra transaction, thay ảnh và cleanup nhưng không nên phụ thuộc dịch vụ bên ngoài. Adapter tách theo profile giúp test có tính lặp lại mà không thay đổi hành vi production.
- Dependency inversion giúp service nghiệp vụ không bị khóa vào một nhà cung cấp lưu trữ ảnh duy nhất.

### 4.3. E2E và contract test

- Auth E2E đạt toàn chuỗi: đăng ký → nhận email qua Mailpit → verify → login → refresh rotation → từ chối refresh token cũ → logout → từ chối refresh sau logout.
- Store E2E đạt: đăng nhập admin → tạo category → tạo quán `PENDING` → upload/thay banner → chỉnh sửa → approve → đọc public API → mở deep-link → reload.
- Health test cho phép Actuator health group nhưng bảo đảm không lộ `details` hoặc `components`.
- Social SDK test chỉ yêu cầu SDK ready khi môi trường E2E cung cấp cấu hình OAuth rõ ràng; local rehearsal không giả vờ kiểm chứng nhà cung cấp thật.
- Toàn bộ Chromium suite đạt **7/7 test**.
- Sáu nhóm utility/contract frontend đạt **14/14 test**.
- `ManagedImageServiceTest` và `MediaCleanupQueueServiceTest` đạt trong Docker build stage.

### 4.4. Failure, restart và persistence rehearsal

- Dừng database khiến readiness trả HTTP 503 với trạng thái `DOWN`; sau khi database khởi động lại, backend phục hồi về `UP`.
- Dừng Mailpit rồi đăng ký hợp lệ khiến backend trả HTTP 500/mã `1015`, phản ánh trung thực việc email quan trọng chưa gửi được; Mailpit sau đó được phục hồi healthy.
- Mô phỏng lỗi xóa banner tạo đúng một cleanup task `PENDING`; scheduler ở chế độ bình thường xử lý queue về 0.
- Restart từng container không làm mất dữ liệu quán trong MySQL volume.
- Flyway history giữ đúng một migration và lần khởi động sau báo schema đã up-to-date.
